# matjip: 평점·리뷰 종합 맛집 추천기

음식/디저트 이름과 지역을 넣으면 여러 출처의 평점과 리뷰를 합쳐 네 가지 목록을 만듭니다.

| 카테고리 | 기준 |
|---|---|
| 웨이팅 무관 · 맛 최우선 | 맛 점수 순 |
| 웨이팅 무관 · 맛+분위기 | 맛·분위기 가중 기하평균 순. 맛·분위기 모두 후보군 중간(40) 이상인 곳만 |
| 웨이팅 적음/없음 · 맛 최우선 | 웨이팅 추정이 "거의 없음/짧음"이고 신뢰도 중간 이상인 곳 중 맛 점수 순 |
| 웨이팅 적음/없음 · 맛+분위기 | 위 두 조건을 모두 만족하는 곳 중 맛+분위기 순 |

```bash
cd matjip_finder
python -m matjip 소금빵 --demo                  # API 키 없이 가상 데이터로 실행
python -m matjip 소금빵 --area 성수동            # 실제 검색 (API 키 필요)
python -m matjip 평양냉면 --area 을지로 --manual my_ratings.csv --format markdown
```

## 먼저 알아야 할 한계

"구글/네이버/카카오 평점 기준"을 그대로 자동화할 수는 없습니다. 출처별로 공식적으로 받을 수 있는 데이터가 다릅니다.

| 출처 | 공식 API로 받는 것 | 받지 못하는 것 | 이 프로그램의 처리 |
|---|---|---|---|
| Google Places API (New) | 평점, 평점 수, 리뷰 최대 5건 | 혼잡도(Popular times) | 자동 수집 |
| 카카오 로컬 API | 장소명, 주소, 좌표, 카테고리 | **별점, 리뷰** | 후보 발굴·병합에만 사용. 별점은 수동 CSV |
| 네이버 검색 API (지역) | 장소 최대 5건 | **별점, 방문자 리뷰, 키워드 리뷰** | 후보 발굴에 사용. 별점·키워드 리뷰는 수동 CSV |
| 네이버 검색 API (블로그) | 글 수, 제목, 요약문 | 본문 전체 | 맛·분위기·웨이팅 텍스트 분석, 웨이팅 언급 비율 |
| 캐치테이블, 다이닝코드, 블루리본, 미쉐린 | 공개 API 없음 | 전부 | 수동 CSV |

- 카카오맵·네이버 플레이스 페이지를 크롤링하면 별점을 얻을 수는 있습니다. 하지만 두 서비스 약관이 자동 수집을 금지하므로 구현하지 않았습니다.
- 네이버 플레이스 별점은 2021년에 폐지됐다가 2026년에 재도입됐습니다. 노출 여부는 사업자가 고르므로 가게마다 별점이 없을 수 있습니다.
- **웨이팅 데이터를 공개하는 곳은 없습니다.** 테이블링, 캐치테이블, 구글 혼잡도 모두 공개 API가 없습니다. 그래서 웨이팅은 리뷰와 블로그 언급으로 *추정*합니다. 요일과 시간대에 따른 차이는 반영하지 못합니다.
- 평점은 맛만이 아니라 서비스, 가격, 웨이팅까지 섞인 전반 만족도입니다. 맛 점수는 평점에 리뷰 텍스트의 맛 언급을 더해 따로 계산합니다.
- 키가 있는 소스만 사용합니다. 구글 키만 있으면 구글 평점과 리뷰 5건이 사실상 전부여서 결과가 빈약합니다. 네이버 키를 함께 쓰거나 수동 CSV를 넣는 것을 권장합니다.

## 설치

Python 3.10 이상이 필요합니다. 기본 기능은 표준 라이브러리만 씁니다.

```bash
cd matjip_finder
pip install -e .            # matjip 명령 설치 (선택)
pip install -e ".[claude]"  # Claude 분석기까지 쓸 때
pip install -e ".[dev]"     # 테스트
```

## API 키

가진 것만 환경변수로 설정하면 해당 소스만 사용합니다.

| 환경변수 | 발급처 | 비고 |
|---|---|---|
| `GOOGLE_MAPS_API_KEY` | Google Cloud 콘솔 → Places API (New) 사용 설정 | 리뷰 필드는 상위 과금 SKU. 무료 한도와 단가는 콘솔에서 확인 |
| `KAKAO_REST_API_KEY` | Kakao Developers → 앱 생성 → REST API 키 | 카카오맵 사용 설정 필요 |
| `NAVER_CLIENT_ID`, `NAVER_CLIENT_SECRET` | NAVER Developers → 애플리케이션 등록 → 검색 API | 일일 호출 한도 있음. 후보 1곳당 블로그 검색 2회 |
| `ANTHROPIC_API_KEY` | Claude Console | `--analyzer claude`에서만 사용 |

## 사용법

```
python -m matjip <음식> --area <지역> [옵션]

--lat/--lng/--radius   검색 중심 좌표와 반경(m). 지정하면 결과가 그 근처로 좁혀짐
--sources google,kakao,naver   사용할 소스 지정 (기본: 키가 있는 것 전부)
--manual FILE.csv      수동 입력 CSV (여러 번 지정 가능)
--analyzer claude      리뷰 분석에 Claude 사용 (기본: 사전 기반)
--top N                카테고리별 추천 수 (기본 3)
--max-candidates N     블로그 보강·분석할 최대 후보 수 (기본 30)
--no-dish-filter       요청 메뉴 언급이 없는 가게도 순위에 포함
--format text|markdown|json
--demo                 내장 가상 데이터로 실행
```

`--area`는 필수입니다. 지역 없이는 "가장 맛있는 곳"을 정의할 수 없고, 검색 API도 지역 단위로 결과를 줍니다.

## 수동 CSV

[`examples/manual_template.csv`](examples/manual_template.csv)를 복사해서 씁니다. 헤더 순서는 상관없고, 없는 값은 비워 둡니다.

| 컬럼 | 의미 |
|---|---|
| `name` (필수), `address`, `lat`, `lng` | 가게 정보. 체인점은 좌표를 넣어야 다른 지점과 섞이지 않습니다 |
| `<플랫폼>_rating`, `<플랫폼>_count`, `<플랫폼>_scale` | 예: `kakao_rating`, `naver_count`, `catchtable_rating`. 만점 기본값은 5, `diningcode`는 100 |
| `taste_votes`, `mood_votes`, `keyword_review_total` | 네이버 키워드 리뷰. "음식이 맛있어요" 수, "인테리어가 멋져요" 수, 키워드 리뷰 참여자 수 |
| `waiting_minutes` | 직접 확인한 평균 웨이팅(분). 넣으면 추정 대신 이 값을 씁니다 |
| `reservable` | true/false |
| `awards` | `\|`로 구분. 예: `블루리본 2\|미쉐린 빕구르망` |
| `reviews` | `\|`로 구분한 리뷰 원문 |

자동 수집 결과와 이름·좌표가 맞으면 하나로 합쳐집니다.

## 점수 계산 방식

모든 점수는 **이번 검색 후보군 안에서의 상대 위치(0~100)**입니다. 플랫폼마다 평점 분포가 다르기 때문입니다(같은 가게도 구글 4.5, 카카오 3.9처럼 나옵니다). 원점수를 그대로 평균하면 왜곡되므로 플랫폼 안에서 순위로 바꾼 뒤 합칩니다. 따라서 후보군 전체가 별로인 동네에서도 1등은 나옵니다. 절대 평가가 아닙니다.

1. **평점 신호**: 플랫폼별 베이지안 평균(가상 리뷰 15개)에서 표준오차 1배를 뺀 보수적 추정치를 구합니다. 이를 플랫폼 안에서 백분위로 바꾸고, `플랫폼 가중치 × log(평점 수)`로 가중 평균합니다. 리뷰 4개짜리 5.0점이 리뷰 400개짜리 4.5점을 이기지 못하게 하려는 장치입니다.
2. **맛 점수** = 평점 신호 45% + 리뷰 텍스트 맛 긍정률 35% + 네이버 "음식이 맛있어요" 비율 20%. 없는 항목은 빼고 비중을 다시 나눕니다. 블루리본·미쉐린은 1건당 +4점(최대 +8)을 더합니다.
3. **분위기 점수** = 리뷰 텍스트 분위기 긍정률 60% + 네이버 "인테리어가 멋져요" 비율 40%. 분위기 근거가 하나도 없으면 "판단 불가"로 두고 맛+분위기 순위에서 뺍니다.
4. **맛+분위기** = 가중 기하평균(맛 0.55, 분위기 0.45). 산술평균을 쓰면 맛 95·분위기 10인 곳이 상위에 오르므로 기하평균을 씁니다. 여기에 더해 둘 다 40 이상이어야 합니다.
5. **리뷰 텍스트 분석**: 리뷰를 절 단위로 나눕니다("분위기는 좋은데 맛은 별로"는 두 절이 됩니다). 측면 명사와 평가어, 부정 표현("맛있지 않다", "안 좋다")을 판정합니다. 블로그 글은 0.6배, 협찬 표기가 보이는 글은 추가로 0.3배 가중치를 줍니다. 요청 메뉴가 같은 절에 나오면 맛 근거를 1.5배로 칩니다.

### 웨이팅 추정

| 신호 | 내용 |
|---|---|
| 언급 비율 | 일반 리뷰 중 "웨이팅 1시간", "오픈런", "줄 서서" 같은 표현의 비율 |
| 방향 | 웨이팅을 언급한 글 중 "길다"와 "없다/짧다"의 비 |
| 언급된 대기시간 | "40분 기다렸어요" 등에서 추출한 분의 중앙값 |
| 블로그 비율 | 네이버 블로그 `"<지역> <가게명> 웨이팅"` 글 수 ÷ `"<지역> <가게명>"` 글 수 |
| 인기도 | 평점 수 + 블로그 글 수 (약한 보조 신호) |

이 신호들을 합쳐 0~1 지수를 만들고 등급을 매깁니다: 거의 없음(<0.2) / 짧음(<0.4, 약 15분) / 보통(<0.65, 약 40분) / 김. 근거가 부족하면 "판단불가"이고, 신뢰도가 "낮음"인 곳은 웨이팅 적은 곳 목록에 넣지 않습니다. **임계값은 실제 대기시간 데이터로 보정하지 않은 휴리스틱입니다.** 값은 [`matjip/config.py`](matjip/config.py)에 모아 두었습니다.

## Claude 분석기 (`--analyzer claude`)

사전 기반 분석은 반어("맛있긴 한데 다시는 안 감"), 비교("옆집보다 별로"), 외국어 리뷰를 놓칩니다. `--analyzer claude`를 쓰면 장소마다 리뷰 묶음(최대 40건)을 Claude에 보내 맛·분위기 점수와 웨이팅 등급을 JSON으로 받습니다. Claude가 판정한 항목만 덮어쓰고, 오류가 나거나 거절되면 사전 분석 결과를 그대로 씁니다.

- 기본 모델은 [`matjip/llm_analyzer.py`](matjip/llm_analyzer.py)의 `DEFAULT_MODEL`이고 `--claude-model`로 바꿀 수 있습니다. 후보 30곳이면 API 요청 30회입니다.
- 리뷰 텍스트는 외부 데이터로 취급하도록 프롬프트에 명시했습니다(리뷰 속 지시문 무시).

## 테스트

```bash
cd matjip_finder && python -m pytest
```

실제 API는 호출하지 않습니다. 구글, 카카오, 네이버, Claude 응답은 가짜 전송 계층으로 검증합니다.

## 알려진 한계

- 실제 API 키로는 검증하지 않았습니다(개발 환경에서 카카오·네이버 API가 네트워크 정책상 차단됨). 응답 파싱은 공식 문서 형식 기준이고 테스트는 가짜 응답으로 했습니다. 첫 실행에서 오류가 나면 `--format json`의 `warnings`를 확인하세요.
- 블로그 검색은 가게명으로 하므로, 이름이 흔한 가게("모모", "브루")는 다른 가게 글이 섞입니다. 지역명을 붙여 줄이긴 하지만 완전하지 않습니다.
- 블로그 요약문은 본문 일부라 글 끝의 협찬 고지를 놓칠 수 있습니다.
- 사전 기반 분석은 한국어 리뷰만 처리합니다.
- 맛 점수 가중치(45/35/20), 플랫폼 가중치, 웨이팅 임계값은 판단값입니다. 정답 데이터로 튜닝하지 않았습니다.
